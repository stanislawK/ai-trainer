# LLM, tools and knowledge rules (ADR-0007 – ADR-0011, ADR-0014 – ADR-0018, ADR-0020, ADR-0027, ADR-0028)

- **Prompts:** only through the registry. Bodies are files at `src/ai_trainer/llm/prompts/<id>/v<N>.<locale>.md`, loaded as `TemplateStr`. Never prompt text in Python strings outside tests (ADR-0008, invariant 1) — test fixtures may hold literal text to script `FunctionModel` responses.
- **Versions:** never edit a template version that has a committed baseline; add `v<N+1>` and switch the registry.
- **Models:** model IDs and keys come from `Settings`, one model per template. Default `Settings` values are stable/GA OpenRouter model IDs only — a preview or beta model is used only inside a `/tune-prompt` comparison run, never promoted as the default. The one exception is `DECISION_MODEL`: a pinned, versioned Jev ID such as `typesafe/jev-1.13` (never `~typesafe/jev-latest`, `jev-latest` or `jev-preview`), allowed because every decision has a fallback (ADR-0020).
- **Decision models (ADR-0020):** Jev (`TypeSafeModel` against OpenRouter's `/api/v1/systemone`, `DECISION_MODEL`) is the default, through `DecisionGatewayPort`, for any step that only picks: classify, route, gate, score, or fill a closed-set draft field (a climbing kind, a sport, a catalogue exercise) that the athlete confirms. Use it wherever it helps; the uses aren't a fixed list. Never use it to produce text, open values (grade strings, numbers, names) or arithmetic. Question sets are files at `src/ai_trainer/llm/decisions/<id>/v<N>.en.yaml`, never strings. Every option needs a description, because Jev never sees field names. Compute numbers and dates in code and pass them in the state. Read probabilities, not the library's 0.5 `bool` cut, and compare them with thresholds from `Settings` that were calibrated on the set's eval dataset: at least 10 labelled cases for a low-risk decision (a wrong answer the athlete sees and fixes before saving, or that costs only a fallback), at least 20 for one that can misroute unseen or touches safety. Index distributions by option name. Every decision has a deterministic fallback (the LLM path, the LLM's own value for a draft field, or the safe side of the gate). A safety decision only adds the safety intent. The state carries the message, recent turns and the athlete's own training context, never identity (no name, email or IDs), under the retention terms ADR-0020 records. Add a set with `/add-decision`.
- **Model and upstream choice:** pick on measured latency, USD per call and evals, never on memory. Live model, price and endpoint facts come from the OpenRouter MCP (`.claude/rules/openrouter-mcp.md`). Provider preferences, reasoning effort and timeouts are per-template `Settings`, never hard-coded (ADR-0026). The one shared group is `onboarding_*`, used by the four `onboarding.<step>` templates, which run off the critical path (ADR-0028).
- **Evals:** a change to a template, a model ID or the router goes through `/tune-prompt` — eval run, no regression, new baseline in the same change. Set the judge model explicitly with `set_default_judge_model(OpenRouterModel(settings.eval_judge_model))`.
- **Accounting:** every gateway call writes exactly one `llm_calls` row — acting user, template ID, version, model, tokens, cost, latency, outcome — on success, timeout and error alike. Tokens and cost come from the provider response, never estimated in code (ADR-0018).
- **Telemetry:** traces are OpenTelemetry over OTLP, off by default, wired only in the composition root, with `include_content=False` so no prompt, completion or athlete message reaches a trace store. No vendor SDK in application code (ADR-0018).
- **Debug log:** `LLM_DEBUG_LOG` (default off) writes every model request, prompt and reply included, as JSON lines under `LLM_DEBUG_LOG_DIR` on the developer's own disk — never to traces, never with a user ID or email, and a write failure never fails a call (ADR-0018 Consequences, #178). Pass new gateway calls the call's `CallRecorder` so they are logged too.
- **Safety:** the `wellbeing_or_injury` intent is handled first (G3).
- **Venues and gym grades (ADR-0027):** the athlete's venues (name, disciplines, grading) may enter extraction context and decision state; a device position never does. Grades stay exactly as typed; a gym's "6" is never drafted as "6A".
- **Onboarding reads (ADR-0028):** one template per step (`onboarding.about_you`, `.goals`, `.level`, `.schedule`), run in the background and never awaited by the request that stored the answer. Outputs are optional fields; unclear means empty, never guessed. Units come back as value plus unit and code converts them. No Jev: the outputs are open values.
- **Dates:** every user-facing template's deps carry `today`, `now_local` and `timezone`. No date tool inside the app's own pipeline, and no wall-clock read outside the `Clock` adapter (ADR-0014).
- **Clarification:** a specialist that cannot proceed returns `Clarification` with concrete options, never a free-text question. The resumed run trusts option IDs, not label text (ADR-0015). An extraction template returns its plugin's question (`ExtractionSpec.question`, a second output type) and code turns it into options; a run resumed with the answer can only draft, and the pick is enforced in code too (ADR-0015, #164 amendment).
- **External sources:** route, crag and place data goes through its port, is cached with `source`, `source_url` and `fetched_at`, and is always shown with that attribution. Only a route, crag or place name leaves the app — never user identity, message text or profile data. Respect the per-user lookup budget; a miss or a low-confidence match becomes a clarification, never a guess (ADR-0016, ADR-0017).
- **MCP tools:** `user_id` only through `current_user_id(ctx)`, never a tool argument; meta from HTTP clients is ignored. Write tools create drafts or proposals only. Every tool returns `ToolResult[T]`; identity/tenancy failures raise, domain failures (bad input, empty result, spent lookup budget) return `success=False` with a `recovery_hint` (ADR-0010).
- **Knowledge:** answers cite their sources; web results are labeled as web; user data never enters the shared knowledge base.
