# ADR 0012 — Web UI

| | |
|---|---|
| Status | Accepted |
| Date | 2026-09-16 |
| Related | PRD-0001 (F1–F6, F9, F10, G5, G10), ADR-0002, ADR-0005, ADR-0015, ADR-0019 |

## Context

The product is chat-first with a few views (F1–F6). The project owner chose FastAPI with HTMX and daisyUI, and designs made in Claude Design.

## Decision

- **Server-rendered** Jinja2 templates with **htmx 4** and **daisyUI 5** on **Tailwind CSS v4**. No SPA.
- **htmx 4.0.0** (released 2026-08-28) uses `fetch()`. SSE (`hx-sse:connect`) is one of htmx 4's core extensions: it ships in the same `htmx.org` package as `dist/ext/hx-sse.min.js`, not inside `htmx.min.js`, and is loaded by its own `<script>` tag with no `hx-ext` attribute. Its npm `latest` tag stays on 2.x until early 2027, so the version is pinned explicitly and both files, htmx and its SSE extension at the same version, are vendored under the static folder (no CDN at runtime).
- **Streaming chat** uses FastAPI's native `fastapi.sse.EventSourceResponse` and `ServerSentEvent`; no `sse-starlette` dependency.
- **Layout:** `src/ai_trainer/web/` holds routes, `templates/` and `static/`. Templates are organized type first, then feature: `layouts/`, `pages/<feature>/`, `partials/<feature>/` and `components/` (ADR-0019). A request with the `HX-Request` header gets a partial; any other request gets the full page.
- **CSS** is built at image build time with the Tailwind standalone CLI and daisyUI's `daisyui.js` Tailwind plugin bundle, loaded via a CSS `@plugin` directive — no Node anywhere. The separate `daisyui-theme.js` bundle defines the custom `trainer-dark` and `trainer-light` themes (ADR-0019); #8 shipped only daisyUI's built-in themes.
- **Designs** from Claude Design map onto daisyUI components and a daisyUI theme; the handoff is ADR-0019.
- **Client JS** is limited to small hand-written files under `static/js/` with no build step, plus vendored libraries under `static/vendor/` (htmx; Chart.js from M2).
- **Shared components** in `templates/components/`: the draft-confirm card (F2), the choice card (F9, ADR-0015) and the route and recommendation cards, which always show their source and fetch date (F10, G10).
- User-facing strings live in templates, not Python, so adding Babel/gettext for Polish later is mechanical (G5).

### Invariants

1. htmx 4 syntax only. Most examples online, and in model training data, are htmx 2: in 4, attribute inheritance needs `:inherited` and 4xx/5xx responses are swapped by default.
2. No Node.js at build or run time; no SPA framework.
3. Styling uses daisyUI components and Tailwind utilities; custom CSS only inside the theme and the glass utilities of ADR-0019.
4. Every non-GET request carries a CSRF token (ADR-0005).
5. HTMX endpoints return HTML. JSON exists only for the documented API.
6. AI-made changes render as confirm / edit / discard cards (F2) and are never saved automatically.

## Consequences

- `.claude/rules/web.md` points agents at the htmx 4 docs through context7 (`/bigskysoftware/htmx/v4.0.0`).
- E2E tests drive the real UI (ADR-0013).
- CSS build gotcha, found at #8: Tailwind v4's automatic source detection respects `.gitignore` to exclude things it shouldn't scan — but the Docker `css-builder` stage has no `.git`/`.gitignore` in its minimal build context, so with automatic detection left on, the daisyUI plugin bundle (`daisyui.js`, sitting next to `input.css` so `@plugin` can load it) gets swept up as a "source" too, and its own literal class-name strings bloat the compiled CSS roughly 6x (verified: 371KB vs 60KB) with unused component styles — a build that is non-deterministic across environments depending on gitignore presence. Fix: `input.css` disables automatic detection outright (`@import "tailwindcss" source(none);`) and scans only the explicit `@source "../../templates"`, making the build deterministic regardless of `.gitignore`.
- Owner-directed amendment, 2026-09-23 (design session, ADR-0019): the Layout decision moves to type-then-feature folders; invariant 3 also allows the ADR-0019 glass utilities; a Client JS decision is added; the `daisyui-theme.js` line now names the custom themes. Everything else is unchanged.
- CSS build flakiness gotcha, found at #37: `scripts/build_css.sh`'s two `curl -f` downloads (the Tailwind CLI binary, `daisyui.js`) occasionally hit a transient 4xx/5xx from GitHub Releases on a fresh CI runner (`exit code: 22`) — invisible before #37 because no CI job ever built the Docker image (`docker compose build`) until the e2e job did (ADR-0013). Both `curl` calls now carry `--retry 3 --retry-delay 2 --retry-connrefused`; a persistent failure (bad version pin, real outage) still fails after the retries, it just no longer trips on one flaky response.
- Dev CSS path, added at #63: `make start`'s app container runs `scripts/dev_start.sh`, which backgrounds `scripts/watch_css.sh` (the pinned Tailwind CLI, `-i input.css -o app.css --watch=always --minify`) and `exec`s the same `uvicorn --reload` command as before. `--watch=always` (not plain `--watch`) is required because a container's stdin is closed by default and plain `--watch` exits as soon as stdin closes. `--minify` is kept in dev too, matching the production build's flags, so dev `app.css` stays close in size to what `css-builder` produces (verified: byte-identical, 104600B, for an unmodified checkout) — `input.css`'s `source(none)` fix (the #8 gotcha) already applies unchanged, since `watch_css.sh` reuses the same `input.css`. No `--poll`: Compose Watch's `sync` action already tar-copies real writes into the container's own filesystem rather than a live bind mount, and inotify picks those up reliably (the same reasoning the #62 bullet above already relies on for Jinja/Python) — verified against the running stack. The watcher fetches the pinned `tailwindcss` binary and the daisyUI bundles at container *start* instead of image *build* time — the tradeoff is a network dependency and a few seconds of extra `make start` startup latency, in exchange for `app.css` never going stale while the container runs. `scripts/css_versions.sh` and `scripts/css_tools.sh` factor the pinned versions and the download logic out of `build_css.sh` so `watch_css.sh` reuses them exactly, rather than risking two copies drifting apart; `build_css.sh`'s own output and the `css-builder` stage are unchanged, but both now need `.dockerignore`'s `scripts` block-then-allowlist pattern extended to the two new shared files, or the `css-builder` stage's `COPY` can't find them. Neither `watch_css.sh` nor `dev_start.sh` needs its own signal handling or cleanup trap: `docker compose stop`/`down` tears down the whole container, host `src/` is never written back to (Compose Watch's `sync` is host→container only), so a `make start` session never leaves `git status` dirty.
- Two more dev-container gotchas found at #63, both invisible until something actually tries to run `watch_css.sh` inside the *final* image rather than the discarded `css-builder` one: (1) the final stage never installed `curl` (only `css-builder` did) — it now does too, guarded by a comment that it's dev-only, since `watch_css.sh` runs from inside the already-built container, not at build time. (2) `COPY . /app` and the css-builder's `COPY --from=` both run as root, so `static/css/` and the files already in it (`app.css`, `theme.css`, `input.css`, `glass.css`) are root-owned in the final image; the container then drops to `USER nonroot`, which can't write there — `chown nonroot:nonroot` on the directory alone isn't enough (it doesn't touch files copied in earlier), so the fix is `chown -R`. Without it, the first dev-mode `tailwindcss` write fails with `EACCES`, silently backgrounded (no error surfaces anywhere obvious) since `dev_start.sh` doesn't wait on the watcher.
- Tailwind v4.3.3's `--watch` only ever *adds* candidates to a session's output — verified directly (both against the pinned CLI standalone and inside this container): removing a class from a template, or reverting a token value, leaves the old rule in `app.css` until the process restarts. No AC needs a removal to disappear live, so this isn't a defect, but it's worth knowing before debugging a stale-looking style during a long `make start` session — `make stop`/`make start` clears it.
- Owner-directed amendment, 2026-10-09 (#82): the Decision said htmx 4.0.0 has SSE in core. It doesn't. The vendored `htmx-4.0.0.min.js` has no `hx-sse` and no `text/event-stream` handling; the [htmx 4.0.0 docs](https://github.com/bigskysoftware/htmx/blob/v4.0.0/www/src/content/extensions/02-hx-sse.md) list `hx-sse` as a core extension loaded from `dist/ext/hx-sse.min.js`. #82 vendors `static/vendor/hx-sse-4.0.0.min.js` from `htmx.org@4.0.0` and loads it after htmx in `layouts/base.html`. Three of its behaviours matter to anyone streaming with it. `hx-sse:connect` reconnects whenever a stream ends unless the element sets `sse.reconnect:false`. It also pauses a stream while the tab is in the background and reconnects on return even with `reconnect:false`, unless `sse.pauseOnBackground:false` is set too; both go in one `hx-config` (`hx-config="sse.reconnect:false sse.pauseOnBackground:false"`). And swapping out the element that owns the connection while its stream is still open aborts the request and logs an `AbortError`. So the chat's reply placeholder owns the connection and stays in the DOM; each event is a `<template hx type="partial">` that appends a chunk or replaces the placeholder's contents, and the server then ends the stream.
