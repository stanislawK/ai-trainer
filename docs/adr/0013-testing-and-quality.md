# ADR 0013 — Testing and quality

| | |
|---|---|
| Status | Accepted |
| Date | 2026-09-16 |
| Related | PRD-0001 (all acceptance criteria), ADR-0001, ADR-0002, ADR-0009, ADR-0019 |

## Context

The workflow is TDD (ADR-0001): each ticket's acceptance criteria become tests before code. AI features are non-deterministic, so tests must be deterministic and quality measurement belongs to evals (ADR-0009).

## Decision

- **TDD:** red → green → refactor. Every ticket AC maps to at least one named test.
- **Layout:**

  ```
  tests/
    unit/          # domain and application, with fakes for ports
    integration/   # real PostgreSQL, adapters, routes, MCP in-memory client
    ops/           # scripts and config outside src/: deploy/, scripts/, compose*.yaml, Grafana JSON
    e2e/           # pytest-playwright against the running compose stack
  ```

- **pytest** with pytest-asyncio in `auto` mode — one async runner for app, Pydantic AI and FastMCP tests. The suite runs in parallel with pytest-xdist (`-n auto --dist loadgroup`, added at #328); tests that share state outside their own transaction run on one worker through an `xdist_group`.
- **Integration tests** use a real PostgreSQL — the `docker compose` Postgres (decided at #3, see Consequences), with each test isolated.
- **LLM code:** agents run with Pydantic AI `TestModel` / `FunctionModel` through `agent.override`, and real model requests are disabled globally (`models.ALLOW_MODEL_REQUESTS = False` in `conftest.py`).
- **MCP:** FastMCP's in-memory `Client(server)`.
- **E2E:** pytest-playwright specs, committed, against the running compose stack, with external services (OpenRouter, Google) mocked at the API boundary. Specs are expensive to write and run (a real browser, the full stack, a dev-seeded session), so `tests/e2e/` stays reserved for genuinely critical, must-not-regress flows — not every UI change. Ad hoc verification during a ticket's own build/verify step (does this page render, does this element show up, does this look right) uses the Playwright MCP tools directly against the running app instead, with no new spec added; a check earns a permanent spec only when it's guarding a flow critical enough to want it to fail loudly forever (a signed-in path, no horizontal overflow, static assets serving).
- **Coverage:** pytest-cov; 100% line coverage on the modules a ticket touches. The global floor only goes up.
- **Gates (GitHub Actions), amended 2026-10-30:** `ruff check`, `ruff format --check`, `mypy --strict`, `pytest` (unit + integration + ops), the import-boundary check (ADR-0003), the OpenAPI drift check and the e2e specs. CI runs on every pull request and every push to `main`, not on pushes to other branches. The checks run as parallel jobs. A pull request runs only the jobs its changed paths need, and a push to `main` runs all of them. One required check, `ci`, passes only when every job passed or was skipped (see Consequences, "Parallel, path-aware CI").
- **OpenAPI:** the snapshot at `docs/api/openapi.json` is regenerated by a script and never hand-edited; CI fails if it drifts.

### Invariants

1. No test calls a real model or external service.
2. Fakes implementing ports are preferred over `mock.patch`.
3. A test is never weakened to make it pass; a wrong test is fixed with a stated reason.
4. Every repository and every user-facing route has a tenancy test (G1).
5. Real-model quality is measured by evals (ADR-0009), not by pytest.

## Consequences

- Skills `/run-tdd` and `/coverage` run this loop; `.claude/rules/tests.md` carries the invariants.
- M0 wires CI, the async runner, the DB fixture and the OpenAPI script.
- Integration tests use the `docker compose` Postgres, decided at #3: they read `DATABASE_URL` from `.env`/the environment like the app does, so `docker compose up -d db` (or the full stack) must be running before `uv run pytest tests/integration`. No testcontainers dependency. CI (#4) runs its own Postgres service the same way, not testcontainers either.
- Warning-filter gotcha, found at #3: `starlette` 1.6.0's `TestClient` imports the deprecated `anyio.abc.BlockingPortal` alias at import time, which this project's `filterwarnings = ["error"]` (ADR-0013) turns into a hard collection error the first time any test imports `fastapi.testclient` or `starlette.testclient` — an upstream bug, not ours, with no fixed release yet. `pyproject.toml`'s `filterwarnings` carries one narrowly-scoped `ignore` for that exact message/module; re-check whether it's still needed next time `starlette` is upgraded.
- CI tooling gotcha, found at #4: `astral-sh/setup-uv`'s `version-file: uv.lock` input only resolves a version when uv itself is a locked dependency (a `[[package]] name = "uv"` entry, from `uv add --dev uv` or similar) — it does not fall back to "latest" like the no-input default path does, so pointing it at a `uv.lock` with no such entry throws `Could not determine uv version from file: uv.lock` and fails the job before any check runs. This project pins uv only in the `Dockerfile` (ADR-0002), not as a project dependency, so `.github/workflows/ci.yml` pins the `setup-uv` step with an explicit `version` matching the Dockerfile instead. Since #310 that version is 0.13.6 and `scripts/check_uv_pins.py` (`make uv-pins-check`, a CI step in the `ci` job, `make check`) fails when the Dockerfile, either `setup-uv` step in `ci.yml`, the one in `evals.yml` or the `uv_build` range in `pyproject.toml` disagrees, naming the file; its tests are in `tests/ops/`. Dependabot bumps each pin in its own PR, so a bump must move all of them in one change or the check fails.
- Per-test isolation, decided at #7: `tests/integration/conftest.py`'s `db_session` fixture joins an `AsyncSession` into a connection-level transaction with `join_transaction_mode="create_savepoint"` (SQLAlchemy's documented pattern for binding a session to an external transaction), then rolls that transaction back at teardown. A test may call `session.commit()` freely — commits only close an internal SAVEPOINT — but nothing it writes is ever visible to another test or connection. No truncation, no testcontainers, no separate test database: same `docker compose`/CI Postgres as #3, same `DATABASE_URL`.
- Migrations run before tests, added at #7: `make test`, `make test-integration` and `make coverage` depend on `make migrate`, and `.github/workflows/ci.yml` runs `alembic upgrade head` after the type check and the import-boundary check (#5), before `pytest` — integration tests that create `VECTOR` columns need the `vector` extension to already exist. `tests/integration/migrations/test_migrations.py` (moved there by the 2026-10-09 amendment below) additionally drives Alembic's own upgrade/downgrade lifecycle directly (not just relying on this pre-step), each test restoring `head` in a `finally` block so one test's failure can't leave the extension missing for every test that runs after it.
- Owner-directed amendment, 2026-09-23 (ADR-0019): E2E specs assert behavior (theme persistence, navigation, overflow at 390 px, served assets), never committed pixel snapshots, because screenshots differ across operating systems and GPUs. Visual fidelity is checked instead by the Playwright MCP parity check against the Claude Design mock, during a web ticket's verify step (`/implement-design`). Signed-in pages are reached in e2e and local browser checks through a dev-only script, `scripts/dev_session.py`, which seeds an active user and a session and prints the cookie. It is a script, not a route, so no authentication bypass ships in the app. It lands with the first e2e ticket.
- Concurrent-write gotcha, found at #37: `scripts/dev_session.py`'s `main()` is the first thing in this codebase that commits real, non-rolled-back rows to `users`/`sessions` outside any single test's own SAVEPOINT (deliberately — that's what a dev-session seeder is for). Running `make e2e` at the same moment as `uv run pytest tests/integration` can therefore transiently trip an unrelated, pre-existing integration test that does an unscoped `SELECT * FROM users` count (`tests/integration/test_auth_route.py`'s `_count_users`), since Postgres's default READ COMMITTED isolation lets that count see another connection's concurrently-committed row. CI never hits this: `.github/workflows/ci.yml`'s `e2e` job only starts after the `ci` job (lint, typecheck, unit, integration) finishes (`needs: ci`). A local run only hits it by deliberately running both suites in parallel in separate terminals.
- Owner-directed amendment, 2026-09-24: the E2E decision above now says specs are reserved for critical flows and that ad hoc Playwright MCP checks (no new spec) are the default for one-off verification — a real browser plus the full compose stack is expensive per ticket, and `tests/e2e/` was starting to look like the place every web ticket would add a spec by default. `.claude/rules/tests.md` and `.claude/skills/apply-ticket`'s web/e2e area notes carry this.
- Owner-directed amendment, 2026-10-09: every test that runs Alembic migrations lives in `tests/integration/migrations/`, and each module there runs in a scratch `<db>_migrations` database on the same Postgres server, not on the shared `DATABASE_URL`. An autouse, module-scoped fixture in `tests/integration/migrations/conftest.py` creates that database, points `DATABASE_URL` at it, upgrades it to head and drops it on teardown. A new migration test goes in that folder, or it would again run on the shared database. This is an exception to the "no separate test database" note above (#7); the `finally`-restores-`head` behavior in the #7 migrations note now acts on the scratch database. The reason: those tests' downgrades (`base` in `test_migrations.py`, earlier revisions elsewhere) dropped `users`, `sessions` and other tables on the shared database, which is the same database `make start` serves. So every local `make test`, `make coverage` or `uv run pytest` deleted the developer's own account and session. The browser's session cookie then no longer resolved, so each run forced a fresh Google sign-in, re-onboarding and an empty chat history. Every other integration test keeps the single shared database and the per-test rollback described at #7. Because the developer's rows now survive, a test can't assume the shared database is otherwise empty. `tests/integration/test_auth_route.py` therefore compares user counts with a count taken at the start of the test and filters audit rows to the test's own user (the #37 gotcha above).
- Parallel run, added at #328: `pyproject.toml`'s `addopts` carries `-n auto --dist loadgroup` ([pytest-xdist](https://pytest-xdist.readthedocs.io/en/stable/distribution.html) 3.8.0), so `make test`, `make test-unit`, `make test-integration`, `make coverage`, CI's `uv run pytest` and a bare `uv run pytest` all run one worker per core; `-n 0` runs serially, and `make e2e` passes it (one browser against the shared stack). On the owner's 10-core Mac the unit run went from 2:39 (the ticket's measurement; 2:54 when re-measured at the start of #328) to about 37 s and the full suite to under a minute, and `make coverage` reports the same lines as a serial run (pytest-cov combines the workers). Integration runs in parallel too: none of it flaked in the verifying runs once the fixes below were in. `tests/conftest.py` puts tests that share state on one worker with a `tryfirst` `pytest_collection_modifyitems` hook (xdist's own hook turns the mark into the group, so it must see the mark first):
  - `db_schema`: `tests/integration/migrations/` and `tests/migrations/` (one `<db>_migrations` scratch database, and `CREATE DATABASE` refuses a second concurrent copy of `template1`), the isolation probe and the vector round trip (they create tables), and every module that commits real users or conversations on its own engine (the `dev_session`, `purge-conversations` and latency-scenario script tests, the concurrent-confirm and concurrent-answer race tests in the session-draft and clarification repository tests, and the `athlete` fixture of `test_request_tracing.py`, reused by `test_request_logs.py` and `test_metrics_wiring.py`) with `test_auth_route`, whose deliberately unscoped user counts would see those rows (the #37 gotcha), and with the real-clock purge of `test_purge_conversations_cli.py`, which would delete them. A new test that commits real rows joins this group;
  - `src_tree`: the import-boundary tests, which write a throwaway module into `src/ai_trainer`, and the wall-clock scan, which would list that module and then fail to read it.

  Gotchas found on the way: a parametrize value made at collection (`str(uuid4())`) needs fixed `ids=`, or each worker collects different test IDs and xdist refuses to start. A session-scoped fixture runs once per worker, so the `isolation_probe` table is now module-scoped in its own test module. macOS scans every newly written executable on its first run, one at a time across processes (about 0.15 s each), so the deploy, backup and restore-drill tests write their stand-ins once per module, not per test. `lint_imports` disables every existing logger, so the import-boundary tests turn them back on afterwards. A test on the shared database can't rely on global counts or a global `DELETE` while other workers commit: the purge tests use a 1990 timeline no other test writes to and count only their own users' rows, and the upgrade-with-data check fingerprints the shared database by revision, table OIDs and the seed users instead of every table's row count. Tests that enable telemetry pass in-memory span and metric sinks, and `test_telemetry.py`, which keeps the real OTLP exporters on purpose, shuts its providers down in the test; before, they kept retrying `127.0.0.1:1` at interpreter exit. The parallel runs also exposed a race in the deploy poller (`deploy/deploy.sh`): a TERM to the whole unit during a step could cut `fail` short after it set `finished`, so no outcome line was printed; `fail` now ignores TERM. `.claude/rules/tests.md` carries the group rule. The owner re-accepts this ADR after the amendment.

- Fast loop, added at #329: the deploy, backup, restore-drill, install-script, cloud-init, Alloy, compose, monitor-password, squawk and Grafana tests (14 modules and `grafana_catalogue.py`) moved from `tests/unit/` to `tests/ops/`. They tested `deploy/` and `scripts/`, not `src/`, and took 130 s of a 155 s serial unit run. `tests/ops` stays in `testpaths`, so a bare `uv run pytest`, `make test` and CI run all of it (3342 tests before and after the move). `make test-fast` runs `tests/unit` and `tests/integration` with `-n auto --ff -x` (about 20 s on the owner's Mac) and is the agent's inner loop in `run-tdd`; `make test-ops` runs `tests/ops` and is added when `deploy/`, `scripts/` or `compose*.yaml` changed. The owner re-accepts this ADR after the amendment.
- Parallel, path-aware CI, an amendment the owner directed on 2026-10-30: a pull request waited about 4 min 45 s for CI (runs 41132012900 and 41117187183, 2026-10-30). The `ci` job took about 2:54 (pytest 75 s, mypy 33 s, cloud-init 18 s, Alloy 14 s, the Postgres service 13 s). The `e2e` job added about 1:50 only after `ci` finished (`needs: ci`), and 40 s of that was the compose build. Every pull request also ran twice, once for `push` (on `"**"`) and once for `pull_request`, and a docs-only branch ran the full suite and e2e. `.github/workflows/ci.yml` changes as follows:
  - **Triggers:** `pull_request`, and `push` to `main` only. The `concurrency` group stays.
  - **Jobs, all started together:** `changes` decides which jobs run. `static` runs ruff, format, mypy, import-linter, the OpenAPI drift check, squawk and the uv pins. `test` runs Alembic and pytest on `tests/unit`, `tests/integration` and `tests/migrations`, with the Postgres service. `ops` runs the cloud-init and Alloy checks and pytest on `tests/ops`, with the Postgres service if a test there needs it. `e2e` runs the compose stack and Playwright. A final job named `ci` (`needs:` all of them, `if: always()`) fails when any of them failed or was cancelled. It keeps the name `main`'s ruleset already requires, so the ruleset doesn't change. `needs: ci` on `e2e` goes away. The #37 concurrent-write gotcha it guarded against needs one shared database, and each job runs on its own runner with its own database.
  - **Path rules:** each job is skipped with a job-level `if:` on the outputs of `changes`, never with a workflow-level `paths:` filter. GitHub reports a job skipped by a conditional as Success, but leaves the checks of a workflow skipped by path filtering Pending, which blocks the merge ([GitHub docs, "Troubleshooting required status checks"](https://docs.github.com/en/enterprise-server@3.0/github/administering-a-repository/troubleshooting-required-status-checks)). `changes` lists the files with `git diff --name-only` against the pull request's base, so no third-party action is added. The rules name the paths that are safe to skip, not the paths that trigger a run, so an unlisted path runs everything:
    - Safe to skip: `docs/**` except `docs/api/openapi.json`, `README.md`, `CLAUDE.md`, `.claude/rules/**`, `.claude/skills/**`. A pull request touching only these skips every job except `ci`. Prompt templates are `.md` files under `src/` and `.claude/hooks/` has tests (`tests/unit/test_guard_release_hook.py`), so "any `*.md`" or "all of `.claude/`" is not safe to skip.
    - `ops` runs only when the change touches `deploy/**`, `scripts/**`, `compose*.yaml`, `Dockerfile`, `Makefile`, `tests/ops/**`, `tests/conftest.py`, `pyproject.toml`, `uv.lock` or `.github/workflows/**`.
    - `e2e` runs only when the change touches `src/**`, `migrations/**`, `tests/e2e/**`, `tests/conftest.py`, `Dockerfile`, `compose.yaml`, `.env.example`, `Makefile`, `pyproject.toml`, `uv.lock` or `.github/workflows/**`.
    - `static` and `test` run on any change that isn't skippable.
    - A push to `main` runs every job, so a path a rule missed still shows up on `main` right after the merge.
  - **Caches:** the e2e image build uses Docker's GitHub Actions cache backend (`type=gha`), through `docker/build-push-action` or `docker buildx bake` before `compose up` ([Docker docs, "Cache management with GitHub Actions"](https://docs.docker.com/build/ci/github-actions/cache/)). It stays only if the ticket measures a saving. Measured at #358 (2026-10-30), the cache was dropped: on main, `docker compose up -d --build` took 35 s (run 41140016488). With the cache, setting up Buildx took 14–15 s, the build with `load: true` took 73 s cold and 21 s warm, and `compose up --no-build` took 13–14 s (run 41141057957 and its e2e rerun). That is 101 s cold and 49 s warm, so even a warm run is 14 s slower. The plain build is already fast: its slow layers are cached in the runner's own engine within the job, and the Buildx builder and the image load cost more than the cache saves. `tests/unit/test_ci_workflow.py` keeps the e2e job and this record in agreement. Playwright's browsers are not cached: Playwright advises against it because restoring takes about as long as downloading ([Playwright docs, "Continuous Integration"](https://playwright.dev/docs/ci)).
  - **Expected:** about 2 min for a code pull request, bounded by `e2e`, and well under a minute for a docs-only one. That is a projection to measure at the ticket, not a figure. Each job pays its own setup (checkout, uv, about 20–30 s), so one run uses more runner minutes. Dropping the duplicate `push` runs uses fewer overall.
  - **Unverified, for the ticket:** whether `main`'s ruleset requires `e2e` as well as `ci` (agents can't read rulesets). A skipped `e2e` reports Success either way, but the owner checks the ruleset after the change. `make check`, `README.md` (the "Every push and pull request runs…" paragraph), `.claude/rules/tests.md` and `/run-tdd` change to match. The owner re-accepts this ADR after the amendment.
