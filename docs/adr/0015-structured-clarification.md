# ADR 0015 — Structured clarification and the choice card

| | |
|---|---|
| Status | Accepted |
| Date | 2026-09-16 |
| Related | PRD-0001 (B3, B17, F9), ADR-0008, ADR-0009, ADR-0012, ADR-0014, ADR-0016 |

## Context

B3 promises a clarifying question when input is ambiguous, and ADR-0008 makes that one free-text question. Real ambiguity is usually a small closed set: three crags have a route of the same name, a log could extend yesterday's session or start a new one, an exercise name matches two movements. Typing the answer is slower than pointing at it, and free text has to be parsed again — a second chance to get it wrong (B17, F9). Every sport hits this, so the mechanism belongs in the pipeline, not in a plugin.

## Decision

- **A typed `Clarification`** model in `src/ai_trainer/llm/`, available as an alternative `output_type` for the router and for every specialist:

| Field | Meaning |
|---|---|
| `question` | one sentence, in the persona's voice (G2) |
| `options` | 2–N `ChoiceOption`: `id`, `label`, `detail`, optional `badge` |
| `mode` | `single` or `multi` |
| `allow_free_text` | whether "let me type instead" is offered |
| `pending` | the draft or intent this blocks |

- A specialist that cannot proceed returns `Clarification` instead of its normal output. The dispatcher (ADR-0008) renders it and suspends that intent; the other intents in the message still run (B14).
- **The answer returns option IDs, not text**, in one htmx POST. The resumed run receives the selected options through its deps and continues where it stopped.
- **One component**, `src/ai_trainer/web/templates/components/choice_card.html`, built from daisyUI (ADR-0012): large tap targets, keyboard-selectable, and a confirm button when `mode` is `multi`.
- `detail` always carries what distinguishes the options — the crag, the date, the grade — never a repeated label.
- `max_clarification_options` in settings (default 5). More candidates than that means narrowing first, or asking a different question.

### Invariants

1. One clarification at a time per intent. Never a list of questions.
2. Options are concrete and selectable. Free text is an escape hatch, never the only route.
3. A clarification writes nothing; the draft stays pending until the athlete picks.
4. The resumed run trusts the option `id`. Label text is for display, and an unknown ID is an error, not a guess.
5. Every clarification path has an eval case (ADR-0009) and an integration test asserting that nothing was written.

## Consequences

- ADR-0008's rule "produces one clarifying question" is replaced by this contract; B3 is refined by B17.
- `.claude/rules/web.md` carries the ID-not-label rule; `.claude/rules/llm.md` points specialists at `Clarification`.
- ADR-0014 (same session or not?) and ADR-0016 (which crag?) both depend on it, so it lands in M1.
- Amended at #162 (the first question, "which sport?"), proposed 2026-10-21 for the owner's review with that ticket's PR. These refine the contract above; the Decision and the invariants stand.
  - **Where the model lives.** `Clarification` and `ChoiceOption` are in `src/ai_trainer/domain/clarification.py`, not `llm/`: the dispatcher (application) and the web layer both read them, and neither may import `llm/` (ADR-0003). `question` is still the persona's one sentence, read from a fixed-reply file (`llm/prompts/sport_question/v1.en.md`, sent as written with no model call), never built in Python (ADR-0008).
  - **Options carry copy keys.** A `ChoiceOption` is `id` and `copy_key`, not `label` and `detail`: user-facing text lives in templates (G5), as a sport's `label_key` does. The card resolves the key to the label and the detail that tells options apart (for a sport, its name and its hint in `components/sport_copy.html`). `badge` and `mode: multi` are in the table above but wait for the first question that needs them; only `single` is built.
  - **When a sport is asked.** One `log_session` intent, Jev sure of the request but not of its sport (`FastRoute.single_intent`), no settling context (a recent draft in the conversation, ADR-0026 step 5), and two or more of the athlete's *loggable* sports (an extraction template, ADR-0006) at or above the plausible floor (`router_fast_plausible_sport_floor`). Options are exactly those sports, likeliest first, cut to `max_clarification_options`. The LLM router is not called: it would only guess. An athlete with one sport, or one whose message names its sport, is never asked.
  - **Storage.** The question is saved as the assistant reply to the log (fixed reply `sport_question`) and as an `open` `clarifications` row with `purpose` `sport`, `message_id` the athlete's log and `draft_id` null. No draft and no session exists until a tap. A reload replays the saved reply and its row; it never asks twice.
  - **The answer.** `POST /clarifications/{id}/answer` carries `option_ids`. An ID the question did not offer, or not exactly one, is a 422 (invariant 4); an answered or skipped question is a 409; another user's, a 404. The resumed run is the sport's ordinary extraction on the original message, in the chosen sport. The row becomes `answered` only after that extraction came through, in one conditional UPDATE, and the draft follows in the same task; a failed extraction leaves the card open to tap again, and two taps at once leave one draft. `POST /clarifications/{id}/abandon` is "Let me type instead": the row becomes `abandoned`, nothing else is written, and the composer takes focus.
  - **With a pain mention.** A sport question never delays the safety reply (ADR-0008 invariant 4, G3): when the screen finds pain, the log is drafted in its likeliest sport and the athlete changes it on the card (F2), with no question.
- Amended at #166 (the second question, "same session or new?", ADR-0014), proposed 2026-10-21 for the owner's review with that ticket's PR. These refine the contract; the Decision and the invariants stand.
  - **A question on a card.** A `same_session` question blocks a stored draft (`clarifications.draft_id`), so it is asked inside that draft's card, in place of its note line, not as a reply line of its own. The rows come from `choice_options` in `components/choice_card.html`, and the question is a fixed reply (`llm/prompts/same_session_question/v1.en.md`) with no model call. The question is stored in the same transaction as its draft (or as the draft's sport change), so a draft never exists without it. The card's Confirm is disabled, and refused with a 409, while the question is open.
  - **Options carry params.** A `ChoiceOption` may carry `params`, values that are not copy and that its copy shows: "Add to the session at {time}" gets `time`, the session's first log as `HH:MM` in the draft's timezone. The "Add" option's ID is the session's ID and "New session" is `new`. The answer trusts only those IDs (invariant 4).
  - **No free-text escape.** The question sets `allow_free_text` false: the card's Discard is the way out. A skip posted to `/clarifications/{id}/abandon` for such a question is a 404, so a draft can't be confirmed without the pick.
  - **No eval case of its own.** The question is decided in code, not by a model. Invariant 5's eval case is the extraction's dating of an after-midnight log about the evening before (`climbing.extract.yaml`, "Last night I sent 2 7A" at 01:10), on which the day comparison depends. The integration test that nothing is written is `tests/integration/test_same_session_repository.py`.
- Amended at #164 (the third question, "which reading?"), proposed 2026-10-21 for the owner's review with that ticket's PR. These refine the contract; the Decision and the invariants stand.
  - **The specialist asks.** A sport's extraction template may return its plugin's question instead of a draft. That is ADR-0008's first specialist-made `Clarification`, the case the Decision describes. Climbing's `climbing.extract` v3 returns `ClimbingExtraction | ClimbingQuestion`, one output tool each (Pydantic AI's list form). The question's readings come likeliest first, each a kind and the grade it turns on as typed, one per kind. Code turns each reading into a `ChoiceOption`: the kind is the ID, `climbing_reading_<kind>` the copy key, and `grade` the param, written in the kind's scale ("Font 7A", "French 7a"). Options are cut to `max_clarification_options`.
  - **What the model sees.** `ExtractDeps.recent` carries the climbing kinds of the athlete's `extract_recent_sessions` latest sessions in the sport, computed by the plugin from their payloads (`ExtractionSpec.recent`, ADR-0006). `ExtractDeps.answers` carries the option IDs a resumed run was given. The template asks only when those sessions hold both boulders and routes and nothing in the message, the athlete's recent messages or the grade's scale settles the kind.
  - **Storage.** The question is saved as a fixed reply (`llm/prompts/reading_question/v1.en.md`, no model call) and an `open` `clarifications` row with `purpose` `reading`, `draft_id` null, and the asking sport in the document (`Clarification.sport`). There is no migration. Asking writes nothing else (invariant 3). In a log of several sports, only the sport that asks is suspended, and the others still draft (B14).
  - **The answer.** It takes the same route as a sport answer: one offered ID, else a 422 (invariant 4). The resumed run is the extraction on the original log, as of when it was sent, with the pick in `answers`, and it can only draft, never ask again. The pick is enforced in code as well as in the prompt: every climb at the grade the tapped option names takes its kind (`SessionExtraction.answered`), and every other climb stays as the message said. A sport answered as climbing may then ask how to read the log.
  - **No guess past an open question.** While a reading question is open on a log, no draft card of that log offers its sport on the sport chip, and a switch to it is refused with a 422. A sport change and a failed draft's Retry run the extraction draft-only, so they never ask. The card's own fields are the way to correct the kind (F2).
  - **Invariant 5.** The eval cases are the `reading:` cases in `evals/datasets/climbing.extract.yaml`, graded by `QuestionMatch`. Answered cases run with the draft-only output the app gives them (`PromptTemplate.output_for`). The integration test that nothing is written is `tests/integration/test_reading_question_repository.py`. Known at promotion (baseline 0.928, 2026-10-21): when only an earlier turn names the kind, v3 still asks sometimes. That is the safe side: one extra tap, never a wrong draft.
- Amended at #206 (gym and cycling ask too), proposed 2026-10-21 for the owner's review with that ticket's PR. These apply the #164 amendment to two more sports; the Decision and the invariants stand.
  - **What they ask.** `gym.extract` v3 returns `GymExtraction | GymQuestion` and `cycling.extract` v3 returns `CyclingExtraction | CyclingQuestion`. A gym question asks about one of two things:
    - which movement an exercise name means ("press" is an overhead or a bench press), `about` `movement`. Each option's ID is a movement, its copy key `gym_reading_movement`, and its params the typed `exercise` and the `movement`.
    - which unit a load typed without one is in, `about` `unit`. The ID is `kg` or `lb`, the copy key `gym_reading_<unit>`, and the params `exercise` and `load` as typed.
    A cycling question asks km or miles for a distance typed without a unit. The ID is the unit, the copy key `cycling_reading_<unit>`, and `distance` the param. A log that is unclear both ways asks about the movement. Its resumed run can only draft, so the load then takes its default unit (ADR-0006, #206 amendment).
  - **When they ask.** Gym asks about a movement only when the name fits two movements and neither the log, the athlete's recent messages nor their recent sessions settle it. A name a lifter reads one way never asks. Gym asks about a unit, and cycling about a distance's unit, only when the recent history mixes the two units. With no history the metric default holds.
  - **The pick in code.** A movement names every exercise typed as the question asked. A unit applies to every load or distance typed without one, even where the resumed run gave it a unit. Every other entry stays as the message said (`SessionExtraction.answered`).
  - **Invariant 5.** The eval cases are the `reading:` cases in `evals/datasets/gym.extract.yaml` and `cycling.extract.yaml`, graded by `QuestionMatch`, which now compares the whole question with its readings in any order. The integration tests that nothing is written are the gym and cycling cases in `tests/integration/test_reading_question_repository.py`. Known at promotion (owner-approved 2026-10-21, `--repeat 3`): `gym.extract` v3 baselines at 0.990 and `cycling.extract` v3 at 0.990. Every case from before passes 3/3 on gym. Two gym reading cases still flip. When one press is in the recent sessions, a bare "press" is sometimes drafted as typed: less specific, never wrong. The other is model noise reading "3x5".
- Amended at #397 (the fourth question, "which exercise is this?", ADR-0031), proposed 2026-10-31 for the owner's review with that ticket's PR. The plan gate approved it. These refine the contract; the Decision and the invariants stand.
  - **A question on a card, one name at a time.** An `exercise` question blocks a stored draft and is asked on its card, as a `same_session` one is (#166), with Confirm refused while it is open. A log with several new names asks in turn, each answer storing the next question in its own transaction, and a same-session question goes first (invariant 1). The entries of one name share one question. `Clarification.subject` holds the name as typed. The question is a fixed reply (`llm/prompts/exercise_question/v1.en.md`).
  - **One option is allowed.** The table's "2–N" becomes "1–N" when `allow_free_text` is true, and a validator refuses one option without it. The free-text escape is then the second route, so invariant 2 holds. ADR-0031 needs this: with no candidate above the floor, the card offers only "Keep my name" and "let me type instead". After the escape the entry stays typed-only, and the name isn't asked again on that draft.
  - **The escape on a card.** `POST /clarifications/{id}/abandon` on an exercise question answers with the draft's card, which asks about its next name, if any. On a confirmed or discarded draft it is a 409.
  - **An edit asks nothing.** A rename clears that entry's settlement, and a question whose name is no longer on the draft is abandoned, so it can't hold Confirm back over nothing. A later answer on the same card may still ask about a renamed entry.
  - **No eval case of its own.** Code decides the question, not a model, as at #166. The integration test that nothing is written is `test_a_question_writes_nothing_but_itself` in `tests/integration/test_exercise_resolution.py`.
- Amended at #402 (the exercise card, F23), owner-directed 2026-11-01 at that ticket's plan gate, on the [Exercise Card mock](https://claude.ai/design/p/d1ddc556-11d3-4434-8e02-9fee28f2efbb?file=Exercise+Card.dc.html). Where these differ from the #397 notes above, these hold. The Decision and the invariants stand.
  - **The exercise question is its own card.** The stored model stays as #397 built it: the question belongs to a stored draft, and a confirm is refused while it is open. Only the view changes. An open exercise question shows in the draft card's place, so Edit, Discard and the sport chip are out of reach until it is answered; "Keep my name" is one tap. Each answer stays as a row above what follows, and the draft's intro line is left out, since the mock has none. A row goes when an edit or a sport change takes its name off the draft. The same-session question stays inside the draft's card.
  - **The question's text is the card's.** `Which exercise is “…”?`, or `I don't have “…” in my list.` with no candidate, live in `components/choice_card.html` (G5). `llm/prompts/exercise_question/v1.en.md` remains the template the question's accounting points at, and no model reads it.
  - **"Let me type instead" opens a name field on this card.** `GET /clarifications/{id}/name` swaps in the field holding the name as typed, and `GET /clarifications/{id}/card` is its Back; neither writes. `POST /clarifications/{id}/name` is "Use this name". It acts as "Keep my name" with the typed name, overriding #397's "the entry stays typed-only" for this path: every entry of the name takes it with `keep_name`, so a confirm makes the custom exercise and its alias, and that name isn't asked about again (B37). The name first written gets no alias, so logging that spelling again asks once more.
  - **Invariant 4 holds.** The question is answered by the `keep` option's ID. The text is a draft edit that no model reads, kept as `typed_name` on the question's document so its row can show it after a reload. A blank name, or one past 200 characters, is a 422 that writes nothing.
  - **`POST /clarifications/{id}/abandon` on an exercise question stays as built,** with no caller left in the UI.
- Europe first, owner-directed 2026-10-25 ([PRD 0008](../prd/0008-ai-training-companion.md) G15). The kg/lb and km/mi unit questions from #206 stay as built. They ask only when the athlete's own history mixes the units, so a metric-only athlete never sees them. New unit or scale questions are added for European ambiguity first. An imperial-only question needs a sign that athletes need it, and a miss on an imperial or American-grade `reading:` case doesn't block a promotion.
